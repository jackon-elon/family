# 入圈、认领与管理流程产品复核

日期：2026-10-02

性质：产品评审建议，尚未视为已实现或最终需求。

## 核心结论

当前产品已经区分家庭圈、同学圈、邀请审批、人物卡和亲属关系，服务端也限制了管理员对已认领资料的修改权限。但「受邀加入 → 确认本人卡 → 接上家庭关系 → 填错后纠正」尚未形成闭环。下一轮应先修好这条主流程，再增加更多称呼规则或装饰性功能。

微信登录、申请加入圈子、认领人物卡、建立亲属关系是四件不同的事。**注册账号时不要求填写“我是某人的伯父”之类的称呼**；称呼依赖观看者，不应作为固定资料保存。家庭圈只保存两位具体人物之间的事实关系，再自动计算称呼。

## 建议的完整流程

1. **受邀申请**：填写圈内常用姓名；用一句话说明谁邀请自己或认识圈内哪位。家庭圈不强迫填精确关系，同学圈要写班级核对信息。提交后只能看到自己的审核状态，不能看到圈内名册。申请超过邀请有效期而无法审批时，明确提示重新邀请。
2. **管理员核对真人**：审批页显示申请姓名、说明、邀请创建人和时间。管理员先判断是否认识、同学圈是否同班；不能仅凭同名或微信昵称认定身份。批准入圈与确认人物卡可分开，防止匆忙认错。
3. **首次入圈确认本人卡**：优先展示可能匹配的未认领卡，供新人选择「这是我」「资料不对」「都不是」。认领须经管理员核对；若确实无卡，再创建本人卡。相似姓名提示可能重复，但不自动合并。管理员预填的姓名、性别、排行和关系须让本人看到并可提出更正。暂不确定时，允许先入圈、后认领；关系图显示待补节点，不猜称呼。
4. **补充家庭关系**：由管理员选择两个具体人物，录入「甲是乙的父母」「两人是兄弟姐妹」「两人是配偶」等事实关系。亲子方向用整句确认；长幼不知道可跳过。普通成员可提交关系建议，不直接改动全圈关系。
5. **发布与纠错**：保存前预览新增、删除或修改的边，以及受影响的称呼和代际位置。明显错误（自我亲子、亲子循环、同一对人物的互斥关系）应阻止或转入待核实；复杂再婚、收养关系应明确标为特殊关系，不能套用普通亲子称呼。管理员处理更正建议时，实际改动与“已采纳”状态一同提交并留痕；失败时建议保持待处理。

## 当前实现中的具体缺口

### P0：下一轮先处理

- **缺少认领入口的完整引导**：加入页只填姓名和自由文字说明；后端虽支持 `claimPersonId`，页面没有传入。批准后页面鼓励直接「创建我的卡」，已有未认领卡容易被重复建立。[申请页](../miniprogram/pages/apply/index.wxml)、[创建人物页](../miniprogram/pages/person-edit/index.wxml)、[服务端加入逻辑](../backend/src/service.ts)。建议加入后的第一屏先完成「认领已有卡／确实没有则新建」分流。
- **关系更正没有闭环**：管理页只可添加或删除关系；点击「接受建议」只改建议状态，管理员仍需另去手动修改，可能出现“已采纳但图没变”。[管理页](../miniprogram/pages/manage/index.ts)、[服务端建议处理](../backend/src/service.ts)。应把变更与处理结果绑定，或至少在变更完成后才允许标记已采纳。
- **服务端没有完整的关系冲突检查**：目前仅检查人物不同、同一条边不重复；亲子环和与同辈关系矛盾的边仍可能保存，影响全圈称呼。[关系创建逻辑](../backend/src/service.ts)。先拦截确定不可能的输入；资料不足和特殊关系以待核实状态展示。
- **关系表单容易填反**：现在用「左边这位／右边这位」和「左边是父母」。应改成「谁是父母 → 谁是子女」，提交前展示整句与影响预览。[管理页表单](../miniprogram/pages/manage/index.wxml)。

### P1：首版上线前补齐

- **误认领可撤销但页面做不到**：服务端支持管理员解绑，管理页没有入口；解绑会清空该卡私人字段。应提供明确的纠错入口、影响提示和本人确认，避免把用户照片、电话等误操作后直接丢失。[解绑逻辑](../backend/src/service.ts)。
- **申请状态不可追踪**：后端已有 `join.mine`，但申请人离开提交成功页后缺少「审核中／已通过／已拒绝／邀请过期」入口；管理员也需要看到待审邀请即将过期的提示。[申请页](../miniprogram/pages/apply/index.wxml)、[申请状态接口](../backend/src/service.ts)。
- **管理对象混在一起**：应在管理页区分「成员账号」「未认领人物卡」「亲属关系」。管理员加人物只是增加一个占位节点，不等于邀请那个人加入；移出成员只撤销访问，不等于删除人物；删关系会改变称呼。每个动作都要显示后果。
- **需求文档仍有旧交互**：现有[需求文档](../亲友关系网小程序需求文档.md)多处写「切换视角、以人物为中心」。已确认的页面方向是按辈分显示整张关系图，并高亮当前成员本人；每位成员打开时称呼相对自己的本人卡计算。下一次修订需求时应统一文案，避免实现两套交互。
- **审计和恢复信息不足**：现有操作记录主要展示动作、目标和时间；更正时还需要操作者、修改前后摘要及关联的建议。关系删除、解绑和移出成员应提供影响确认、短期恢复方案以及必要的当事人通知。[管理页记录](../miniprogram/pages/manage/index.ts)、[服务端审计](../backend/src/service.ts)。
- **微信扫码邀请尚未接通**：当前二维码仍是预留位；既然微信分享和扫码均是已确认需求，正式上线前要共用同一份一次性邀请并完成真机联调。[邀请页](../miniprogram/pages/invite/index.wxml)。

### P2：可在核心流程稳定后做

- 重复人物卡合并：先提供人工标记和预览，不能按姓名自动合并；合并需处理关系边、认领状态、私人资料及撤销路径。
- 特殊家庭关系：当前持久化只支持普通亲子、配偶和兄弟姐妹；再婚、收养、继亲等需要专门关系类型或明确的待核实路径，避免误算普通血缘称呼。

## 管理员权限边界

- 管理员可新增和修正**未认领人物卡**的姓名、性别、排行等维持关系所需的最少资料；可审核加入、认领，添加或纠正关系，邀请和移出普通成员。
- 已认领成员的照片、城市、手机号、微信号等由本人维护。管理员只有在本人按字段授权后才能代维护授权字段；管理员身份本身不能越过可见范围，更不能代替本人开放电话。
- 普通成员可直接编辑本人资料、提出他人资料或关系的更正建议。关系建议进入管理员待处理队列，不直接改写全圈图。
- 关系边牵涉已认领人物时，管理员仍可纠正，但应记录理由并通知相关当事人，给出争议反馈入口。

### 「管理员加人」应拆成明确动作

1. **添加人物卡**：家人还没有使用小程序，也能先建只有姓名等最少信息的卡并接入关系图；这一步不会给对方访问权。
2. **邀请加入**：管理员向真人发送短期一次性邀请；这一步不会自动创建或认领人物卡。审批时核对真人身份。
3. **确认人物卡**：已有卡走认领审核；没有卡才新建本人卡。处理候选重名、错卡时不按姓名自动绑定。
4. **维护资料**：未认领卡只改基础关系资料；已认领卡的私人字段由本人改，或由本人授权管理员按字段代改。关系边的管理员更正走影响预览和记录。

管理页宜把按钮分别写成「添加未加入的家人」「邀请加入圈子」「审核认领」「整理关系」，避免一个「加人」入口同时承担四种含义。

## 建议验收场景

1. 管理员已建立「张三」卡并连好关系；张三通过邀请加入后选择已有卡，管理员核准，系统不再创建第二张张三卡。
2. 被转发邀请的人填了与圈内人相同的姓名，管理员不批准；申请人始终看不到圈内人物和联系方式。
3. 新人不确定自己与哪位亲戚的关系，先入圈但暂不发布关系；关系图不显示错误称呼。
4. 管理员把「父亲 → 儿子」填反，保存前能看懂方向和受影响人物；若已保存，提交更正后实际关系与建议状态一起更新，相关称呼重新计算。
5. 误认领后管理员解绑并改绑，私人资料不会无提示地消失，操作可追溯。
6. 管理员移出成员后该账号立即失去访问权，关系图保留不含私人资料的必要节点；删除人物与删除关系分别提示影响。

## 待产品确认的两项取舍

1. **认领放在何时**：建议「先审核入圈、再认领人物卡」，以减少未获批者接触名册。管理员可以在审批时记录候选卡，但绑定前仍需申请人确认。
2. **关系建议谁能发布**：建议第一版由管理员最终发布，成员和被涉及的本人均可提出异议；以后再根据圈子活跃度考虑共同编辑。
